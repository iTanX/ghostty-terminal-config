# Intel AX200 蓝牙无法开启、开关立即回到关闭：排查与修复记录

记录日期：2026-11-01。

## 1. 给后续协助修复的智能体

先检查当前设备和日志，再决定是否使用本文的修复命令。本次已确认的故障是：**Intel AX200 蓝牙控制器在开机初始化时读取芯片版本超时，BlueZ 因而没有可用控制器；重新加载 `btusb` 驱动后初始化成功，蓝牙恢复开启。**

用户随后补充，故障前曾不小心碰掉电源。突然断电是可能的诱因，但现有证据不能证明具体触发机制，也没有证明是 USB 自动休眠、固件文件损坏或硬件损坏。

复现时建议按以下顺序处理：

1. 先保存故障现场：检查 USB 硬件、控制器、禁用状态、服务和内核日志。
2. 如果证据与本文吻合，重新加载 `btusb` 驱动。
3. 验证固件加载、控制器注册和开启状态，再由用户实际连接设备。
4. 若未恢复，保留新日志继续定位，不要反复无条件重载驱动或直接安装其他修复方案。

本文只新增故障记录。本次修复没有安装软件、修改持久配置、清除配对记录或新增开机服务。

## 2. 问题现象与本次环境

### 2.1 用户可见现象

- 蓝牙突然不可用，GNOME 设置显示蓝牙关闭。
- 点击开启后，开关立即跳回关闭。
- 用户补充：故障前发生过意外断电。

### 2.2 已验证环境

| 项目 | 本次值 |
|---|---|
| 系统 | Debian 13，GNOME 桌面 |
| 内核 | `6.12.113+deb13-amd64` |
| 内核软件包版本 | `6.12.113-1` |
| BlueZ | `5.82-1.1` |
| `firmware-iwlwifi` | `20250410-2` |
| 蓝牙硬件 | Intel AX200 Bluetooth |
| USB 厂商／产品 ID | `8087:0029` |
| 驱动 | `btusb`、`btintel` |
| 本次控制器 | `hci0` |
| 本次 USB 节点 | `/sys/bus/usb/devices/1-5` |

控制器编号、USB 总线编号和设备路径可能变化，下次应重新检测，不要直接写入本文记录的 sysfs 路径。

## 3. 定位检查步骤与证据

以下检查不会主动更改蓝牙配置。读取完整系统日志通常需要管理员权限；普通用户看到 `-- No entries --` 且有权限提示时，不能据此认定没有错误日志。

### 3.1 检查硬件枚举与驱动

```bash
# 查看 USB 蓝牙硬件是否仍被识别。
lsusb

# 查看蓝牙相关驱动是否已加载。
lsmod | rg 'bluetooth|btusb|btintel|btmtk|btrtl|btbcm'

# 记录当前内核和软件包版本。
uname -r
dpkg-query -W bluez firmware-iwlwifi
```

本次 `lsusb` 包含：

```text
Bus 001 Device 003: ID 8087:0029 Intel Corp. AX200 Bluetooth
```

`btusb`、`btintel` 和 `bluetooth` 等模块已经加载。这说明 USB 层仍能枚举设备，但不能证明蓝牙控制器已经初始化成功。

如果硬件根本不在 USB 列表中，应先排查设备供电、USB 枚举、固件／BIOS 设置等，不要直接套用本次结论。

### 3.2 检查服务与 BlueZ 控制器

```bash
# 查看服务和 BlueZ 注册的控制器。
systemctl status bluetooth --no-pager -l
bluetoothctl list
bluetoothctl show

# 查看 BlueZ 的 D-Bus 对象树。
busctl --system tree org.bluez
```

本次故障时：

- `bluetooth.service` 为 `active (running)`。
- `bluetoothctl list` 没有列出控制器。
- `bluetoothctl show` 输出 `No default controller available`。
- D-Bus 对象树只有 `/org/bluez`，没有控制器对象。

因此，服务进程存活不等于蓝牙可用，本次需要继续排查底层控制器初始化。

### 3.3 排除无线禁用和飞行模式

安装了 `rfkill` 时可执行：

```bash
# 查看是否被软件或硬件禁用。
rfkill list
```

本次没有安装 `rfkill` 命令，但内核提供了相同状态信息，无需为了完成检查立即安装软件：

```bash
# 读取每个无线设备的名称、类型及软硬件禁用状态。
python3 -I - <<'PY'
from pathlib import Path

for device in sorted(Path('/sys/class/rfkill').glob('rfkill*')):
    print(f'[{device.name}]')
    for name in ('name', 'type', 'soft', 'hard', 'state'):
        path = device / name
        if path.is_file():
            print(f'{name}: {path.read_text().strip()}')
PY
```

本次蓝牙 `hci0` 的结果为：

```text
name: hci0
type: bluetooth
soft: 0
hard: 0
state: 1
```

`soft: 0`、`hard: 0` 表示没有被软件或硬件禁用。这里的 `state: 1` 表示无线未被禁用，不代表 BlueZ 控制器已成功开启。

GNOME 桌面还可检查飞行模式：

```bash
# 仅适用于提供此 D-Bus 接口的 GNOME 会话。
gdbus call --session \
  --dest org.gnome.SettingsDaemon.Rfkill \
  --object-path /org/gnome/SettingsDaemon/Rfkill \
  --method org.freedesktop.DBus.Properties.GetAll \
  org.gnome.SettingsDaemon.Rfkill
```

本次 `AirplaneMode`、`HardwareAirplaneMode`、`BluetoothAirplaneMode`、`BluetoothHardwareAirplaneMode` 均为 `false`，排除了飞行模式。

### 3.4 检查底层控制器初始化状态

```bash
# hciconfig 是旧工具；本次系统已安装，用于补充诊断。
# 如果系统没有此命令，继续读取内核日志即可。
timeout 8s hciconfig -a
```

本次故障时的关键输出：

```text
hci0: Type: Primary  Bus: USB
    BD Address: 00:00:00:00:00:00  ACL MTU: 0:0  SCO MTU: 0:0
    DOWN
    RX bytes:0 acl:0 sco:0 events:0 errors:0
    TX bytes:4 acl:0 sco:0 commands:1 errors:0
```

sysfs 中虽有 `hci0`，但地址全零、MTU 为零、没有收到事件，结合 BlueZ 没有控制器，说明初始化未正常完成。

本次还尝试过 `btmgmt info`，命令持续等待，最终停止。下次如需使用，应设置超时并按需使用管理员权限，例如 `sudo timeout 8s btmgmt info`；不要让诊断命令无限等待，也不要仅凭其超时判断硬件损坏。

### 3.5 读取内核日志，确认直接故障

```bash
# 查看本次启动的蓝牙、固件和相关驱动日志。
sudo journalctl -b -k --no-pager \
  -g 'Bluetooth|bluetooth|btusb|btintel|firmware' -n 160

# 查看蓝牙服务日志。
sudo journalctl -b -u bluetooth --no-pager -n 100
```

本次关键内核日志：

```text
11月 01 16:37:57 Hikari kernel: Bluetooth: hci0: command 0xfc05 tx timeout
11月 01 16:37:57 Hikari kernel: Bluetooth: hci0: Reading Intel version command failed (-110)
```

`-110` 表示超时。驱动向芯片发送读取 Intel 版本的命令后没有得到响应，初始化因此失败。

本次通过 `sudo -n` 读取日志时提示需要密码，随后使用系统认证窗口成功读取。智能体无法交互输入 sudo 密码时，可使用以下只读命令申请图形认证，或请用户在终端执行上面的 sudo 命令：

```bash
# 需要可用的桌面认证代理；密码只在系统认证窗口输入。
timeout 55s pkexec /usr/bin/journalctl -b -k --no-pager \
  -g 'Bluetooth|bluetooth|btusb|btintel|firmware' -n 160
```

认证失败或被取消时，不应视为已读取日志，也不要向用户索要密码文本。

## 4. 最终定位结论与证据边界

本次确认的故障链路为：

```text
AX200 在开机初始化时不响应读取版本命令
→ 内核报告命令超时（-110）
→ 控制器未完成初始化，BlueZ 无可用控制器
→ GNOME 蓝牙开关无法保持开启
```

重新加载驱动后，同一设备成功响应并完成固件加载，进一步支持这是一次可通过重新初始化恢复的故障。

需要保留以下边界：

- **突然断电：可能诱因。** 用户确实报告了意外断电，但没有对照实验或更底层证据证明断电如何触发这次超时。
- **USB 自动休眠：未证明是原因。** 故障时观察到设备 `power/control=auto`、`power/runtime_status=suspended`，仅凭这些状态不能认定自动休眠导致故障，本次没有修改该设置。
- **固件缺失或损坏：没有支持证据。** 重载后现有固件成功加载，无需因此重装固件。
- **硬件损坏：没有明确迹象。** 重载后恢复正常，但这不构成对所有硬件问题的全面排除。
- 日志中的 `iwlwifi ... failed to load iwl-debug-yoyo.bin (-2)` 属于 Wi-Fi 驱动的另一条信息，本次没有证据将其与蓝牙版本读取超时关联，不应据此偏离蓝牙排查。

## 5. 已验证有效的修复方案

### 5.1 重新加载蓝牙 USB 驱动

先保存故障日志，再执行：

```bash
# 会暂时断开所有由 btusb 驱动的蓝牙设备，请先保证有其他输入方式。
# 仅在卸载成功后重新加载，不强制卸载模块。
sudo modprobe -r btusb && sudo modprobe btusb
```

本次智能体通过图形认证实际执行的等价命令为：

```bash
# 需要桌面认证代理；用户在系统窗口完成管理员认证。
timeout 55s pkexec /bin/sh -c \
  '/usr/sbin/modprobe -r btusb && /usr/sbin/modprobe btusb'
```

两种方式选择一种即可，无需依次执行。驱动重新加载后，等待数秒让固件下载与控制器注册完成，再执行后续验证。

本次没有重启电脑或重启蓝牙服务，仅重载 `btusb` 就恢复。若卸载报模块正在使用，应先记录报错并排查占用，不要使用强制卸载。

### 5.2 确认开启与恢复结果

```bash
# 控制器应重新出现在列表中。
bluetoothctl list

# 通过正常接口开启蓝牙。
timeout 8s bluetoothctl power on

# 检查状态；应有 Powered: yes，本次还显示 PowerState: on。
bluetoothctl show

# 如系统提供此工具，应看到有效地址、非零 MTU 和 UP RUNNING。
timeout 8s hciconfig -a

# 查看最近 3 分钟的蓝牙初始化日志，对比修复前的旧错误。
sudo journalctl -b -k --since '-3 minutes' --no-pager \
  -g 'Bluetooth|btusb|btintel' -n 100
```

本次修复后确认：

```text
Controller EC:8E:77:07:66:2D Hikari [default]
Powered: yes
PowerState: on
Changing power on succeeded
```

`hciconfig -a` 显示有效地址 `EC:8E:77:07:66:2D`、非零 MTU 和 `UP RUNNING PSCAN`。

2026-11-01 16:42:47 至 16:42:49 的内核日志包含：

```text
Bluetooth: hci0: Found device firmware: intel/ibt-20-1-3.sfi
Bluetooth: hci0: Firmware loaded in 1423108 usecs
Bluetooth: hci0: Device booted in 16606 usecs
Bluetooth: hci0: Found Intel DDC parameters: intel/ibt-20-1-3.ddc
Bluetooth: hci0: Applying Intel DDC parameters completed
Bluetooth: hci0: Firmware revision 0.3 build 132 week 3 2024
Bluetooth: MGMT ver 1.23
```

验证范围：已确认本次会话中固件加载、控制器注册和开启成功；未在本次排查中验证实际外设连接、下一次重启或长期稳定性。旧的开机超时日志会留在本次启动的 journal 中，判断恢复应看修复时间之后的新日志。

如果系统状态正常但设置页面仍显示旧状态，可关闭设置窗口后重新打开，再实际连接蓝牙设备验证。

## 6. 如果重载后仍无法恢复

1. **再次采集日志。** 对比重载前后的错误，确认是否仍为读取版本超时；若变成缺固件、USB 断连或其他错误，应按新证据处理。
2. **检查禁用和服务状态。** 如果此次确实被 rfkill 禁用，或服务启动失败，应处理对应问题，不要认定与本次原因相同。
3. **考虑彻底断电复位。** 若初始化仍卡住，可请用户保存工作、正常关机，再断开外部电源约 30 秒后开机。这是后备建议，本次未执行或验证；笔记本仅拔充电器不代表内部设备已断电，应遵循设备厂商的复位方法。
4. **反复出现再调查长期原因。** 记录发生时间，以及与冷启动、重启、睡眠恢复和意外断电的关系，再比较内核、固件版本及电源管理行为。不要仅凭一次故障永久禁用省电、添加自动重载服务或重装 BlueZ。

完整重启或断电操作应由用户保存工作后配合完成，智能体不要自行直接关机。
