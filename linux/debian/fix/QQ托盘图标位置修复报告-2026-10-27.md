# QQ 托盘图标位置无法记忆：诊断与修复报告

- 日期：2026-10-27（北京时间）
- 操作范围：用户目录中的 Status Tray 本地插件，以及该插件的 QQ 排序项。
- 系统：Linux / GNOME Shell 48.7（Wayland）。
- 插件：Status Tray 2.8，扩展版本 33，UUID 为 `status-tray@keithvassallo.com`。
- QQ：linuxqq 3.2.34-53644，可执行文件 `/opt/QQ/qq`。
- 上游项目：https://github.com/keithvassallomt/status-tray

## 1. 现象与结论

QQ 托盘图标在拖动排序后，退出并重新打开会跑到末尾。

根因是 QQ 没有提供可用的稳定托盘身份，Status Tray 的现有识别链也没有针对普通本地进程的最后兜底，因此使用每次启动都会变化的 D-Bus 连接号保存 QQ 的位置。重启后新连接号无法命中旧的排序记录。

本次已安装通用的可执行文件身份兜底，并将已确认属于 QQ 的排序记录从 `:1.340` 迁移为 `executable:/opt/QQ/qq`，保留它在原排序数组中的位置。

**首次实施时的状态：代码与配置已写入，38 项针对性检查通过；当时桌面会话仍运行缓存中的旧插件代码，需要注销后重新登录。首次实施没有执行实际 QQ 退出、重开验收。**

**后续反馈与处理（2026-10-27）：用户反馈 QQ 已正常；随后发现 LocalSend 仍无法记住位置。LocalSend 属于“随机但非空的 SNI ID”，通过已有名称匹配设置解决，无新增代码修改。详见第 11 节。

## 2. 诊断证据

通过只读 D-Bus 查询，QQ 当时注册为 `:1.340/StatusNotifierItem`：

| 字段 | 实际结果 | 对识别的影响 |
|---|---|---|
| SNI `Id` | `chrome_status_icon_1` | Chromium 通用名称，插件有意不将其视为可靠应用 ID |
| `Title` | 空字符串 | 不能取得应用名称 |
| `ToolTip` | 图标名、图标像素、标题、描述均为空 | 不能从提示标题生成稳定 ID |
| `IconName` | `status_icon_0` | 通用图标名，不能唯一识别应用 |
| `IconThemePath` | `/tmp/org.chromium.Chromium.j2A1Lr` | 随机临时目录，无法生成 Flatpak 应用标识 |
| D-Bus 所属进程 | PID 20176 | 仅用于追溯进程，不存入稳定标识 |
| `/proc/20176/exe` | `/opt/QQ/qq` | 可以取得稳定的本地应用可执行文件路径 |

修改前排序配置为：

```text
[':1.242', ':1.340', 'wechat', ':1.300', 'magpie', 'ytXmd3YOvF', 'Motrix_status_icon_1', 'Snipaste']
```

QQ 的当前连接号确实出现在排序中。其他历史临时编号无法仅凭现状可靠归属，本次没有清理它们。

插件原有的 “Match by App Name” 依赖 SNI 标题、提示标题等名称信息。QQ 这些信息为空，不能单靠启用此选项解决。

## 3. 实施方案

这是通用的最后兜底，不包含 QQ 专属路径判断或 QQ 专属标识规则。

1. 继续优先采用插件原有的 SNI ID、Flatpak 标识、提示标题、用户名称别名。
2. 保留对象路径已经提供的非通用标识。
3. 如果仍只能使用以 `:` 开头的临时 D-Bus 连接号，异步调用 `GetConnectionUnixProcessID`。
4. 异步读取 `/proc/<pid>/exe` 指向的可执行文件，生成 `executable:<完整路径>`。
5. 托盘和设置界面调用同一个 `appIdentity.js`，保证排序标识一致。
6. 查询失败、进程退出或访问受限时返回空结果，保留原有行为。托盘对象已销毁或查询取消时不再更新对象。

使用完整路径而不是文件名，避免 `/opt/AppA/qq` 与 `/opt/AppB/qq` 被误认为同一应用。PID、连接号不会写入新稳定标识。

为了避免明显误识别，兜底跳过已知共用运行程序，例如 Python、Java、Node、Electron、GJS、Ruby、Perl、PHP、Lua、Shell、Flatpak 代理，以及临时目录、运行时目录、沙箱 `/app` 路径、已删除的可执行文件。该排除规则是保守规则，不能覆盖所有可能的共用运行程序。

## 8. 多账号、多图标及兼容边界

- 活跃托盘图标仍通过不同的 D-Bus 连接和对象路径管理，不因固定应用 ID 相同就合并成一个图标。
- 软件提供可靠的不同 SNI ID 或对象路径标识时，继续保留区别。
- 如果同一个可执行文件产生多个完全缺乏可区分信息的图标，它们将共用应用级排序 ID。图标仍可同时显示，但无法保证各自跨重启的先后顺序或独立位置。
- 这些图标也会共用按应用 ID 保存的图标覆盖、效果和显示开关等设置。设置界面在相同 ID 下的独立调整不应视为受支持。
- 未知共用宿主程序可能仍产生身份碰撞；本方案不承诺所有应用都能自动正确区分。
- 可执行文件安装路径发生变化时（尤其版本号目录、AppImage 临时挂载目录）不一定能保留身份。本次 QQ 的固定路径 `/opt/QQ/qq` 不含版本号。
- 上游扩展更新可能覆盖 `extension.js`、`prefs.js` 或新增文件。更新后先核对代码、版本和备份，结合新版实现重新评估补丁，不应直接把旧的整个目录覆盖回新版本。

## 9. 回滚步骤

回滚会恢复修改前的代码和插件全部设置，之后对该插件所做的配置变更也会被旧快照覆盖。应在确实需要回滚时执行。

先备份届时的现状，再恢复两个原文件、删除本次新增模块，并载入旧设置：

```sh
tray_dir="$HOME/.local/share/gnome-shell/extensions/status-tray@keithvassallo.com"
backup_dir="$HOME/.local/share/status-tray-backups/20261027-010708"
rollback_save="$HOME/.local/share/status-tray-backups/before-rollback-$(date +%Y%m%d-%H%M%S)"

mkdir -p "$rollback_save"
cp -a "$tray_dir" "$rollback_save/extension"
dconf dump /org/gnome/shell/extensions/status-tray/ > "$rollback_save/settings.dconf"

cp -a "$backup_dir/original-extension/extension.js" "$tray_dir/extension.js"
cp -a "$backup_dir/original-extension/prefs.js" "$tray_dir/prefs.js"
rm -f "$tray_dir/appIdentity.js"
dconf reset -f /org/gnome/shell/extensions/status-tray/
dconf load /org/gnome/shell/extensions/status-tray/ < "$backup_dir/settings-before.dconf"
```

回滚后同样需要注销再登录，让 GNOME 放弃已缓存的新模块。如果插件已经升级，不应直接执行以上旧版本文件恢复步骤，需先核对当前版本。

## 11. LocalSend 后续问题及处理（2026-10-27）

用户反馈 QQ 已恢复正常，但 LocalSend 出现同样的重启后排序丢失。本节记录后续诊断与配置修复。

### 原因与 QQ 的区别

LocalSend 版本 1.18.2（build 64），可执行文件为 `/opt/localsend_app/localsend_app`。

初次调查中的 LocalSend 托盘 ID、对象路径末段是 `ytXmd3YOvF`，本次启动已变为 `QE5rRRbucH`，路径为 `/org/ayatana/NotificationItem/QE5rRRbucH`。两次 ID 都出现在排序设置中，说明排序确实绑定了随启动变化的随机字符串。

但 LocalSend 始终有非空的 SNI ID，插件将其作为可靠 ID；对象路径也含有同一个随机字符串。因此本次 QQ 的“只剩临时连接号时才兜底”不会介入。通用兜底不能自动判断任意非空字符串是否真的稳定，不能把所有现有 SNI ID 都强行改成进程路径，否则会破坏有意区分的多个图标。

与 QQ 不同，LocalSend 的 SNI `Title` 非空，实际为 `org.localsend.localsend_app`。插件自带的 “Match by App Name” 可以直接解决此类随机 ID。

### 本次配置变更

未再次修改或新增插件代码。三个补丁文件的 SHA-256 均与首次修复完成后的记录一致。

通过 D-Bus 重新确认所属进程为 `/opt/localsend_app/localsend_app`，读取当前 ID 与标题后，按插件实际的 `cleanAppName()` 规则得到名称：

```text
Org.Localsend.Localsend App
```

该名称是插件自动清理标题产生的配置键，大小写和下划线变化来自插件原有逻辑。

设置 `title-aliases` 为：

```text
{'Org.Localsend.Localsend App': 'Org.Localsend.Localsend App'}
```

效果等同于在 LocalSend 的图标自定义界面开启 “Match by App Name”。

将当前 LocalSend 排序项 `QE5rRRbucH` 换成以上名称，保留当前项的位置；删除此前确认属于同一 LocalSend 的历史 ID `ytXmd3YOvF`。修改后的排序为：

```text
[':1.242', 'executable:/opt/QQ/qq', 'wechat', ':1.300', 'magpie', 'Org.Localsend.Localsend App', 'Motrix_status_icon_1', 'Snipaste']
```

迁移脚本也检查了旧 ID 下的图标、效果、显示等按应用配置；这些配置实际为空，因此最后对比确认只有 `app-order` 和 `title-aliases` 两个键的值改变。QQ 的稳定排序标识保留。

### 验证与生效

- 12 项针对性检查通过，使用插件实际的托盘和设置界面解析方法，验证旧 ID `ytXmd3YOvF`、当前 ID `QE5rRRbucH`、模拟未来新 ID `newRandom42` 都映射到同一稳定名称。
- 检查稳定排序项恰好一项，两个旧 ID 已移除，QQ 排序仍存在。
- 插件的错误列表为空。
- `title-aliases` 是插件已有的实时监听设置，本次无需注销即可由运行中的插件重新解析身份。
- 未主动退出或重启 LocalSend；本次没有实际跨启动视觉验收。用户可以完全退出、重新打开 LocalSend 进行确认。若目标位置需要调整，启用名称匹配后重新拖动一次即可。
