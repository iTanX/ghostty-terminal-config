# Linux 配置脚本维护规范

本规范适用于 `linux/` 下各发行版配置，包括现有的 Mint、Ubuntu，以及后续新增的 Debian 13 配置。新增平台时，先对照现有平台的对应文件，沿用相同结构。

## 适用范围

重点统一以下文件：

- `one_click_setup/01-basic-config.sh`
- `one_click_setup/02-development-environment.sh`
- `one_click_setup/03-input-method-init.sh`
- `one_click_setup/04-input-method-update.sh`
- `terminal/install.sh`
- `terminal/configure-fonts.sh`
- `terminal/fontconfig/` 下的规则文件

## 步骤与注释

- 相同任务采用统一的大步骤、小步骤、执行顺序、注释、序号和分隔格式。
- 注释只描述当前步骤，不写平台差异、平台背景或实现原理。平台检查、安装来源、桌面设置等实际执行代码按平台保留。
- 对应文件除了平台所需的执行代码差异外，不应出现无关的注释、空行或格式差异，尽量减少跨平台比较时的差异。
- 平台独有的执行代码放在对应任务的位置，不因此改变其他共同步骤的编号和顺序。
- Shell 大步骤统一使用以下格式：

```bash
# ==============================================================================
# 安装终端工具
# ==============================================================================
```

- 小步骤使用 `# 1. 步骤名称`，子步骤使用 `# 1.1 步骤名称`，依次编号。每个大步骤内从 `1` 开始编号，不混用其他分隔或编号样式。
- Fontconfig 等非 Shell 文件使用其原生注释语法，保持对应规则的步骤说明一致。
- 写入配置文件的标记注释、受控配置块边界属于程序使用的数据，不能因清理注释而删除或破坏。

## 软件安装分组

- 一个软件需要添加源、安装及专属配置时，将这些操作归入该软件的独立小步骤，按“配置软件源 → 刷新索引 → 安装 → 专属配置”的依赖顺序组织。
- 例如 Mint 的 Ghostty PPA 配置和 Ghostty 安装应放在一起，不要将源配置与安装拆散到不同任务中。
- 安装过程所需的辅助依赖与主线软件分开执行 `apt install` / `apt-get install`。例如解压字体包所需的 `unzip` 应放在依赖安装组，不混入终端工具与插件安装组。
- 两个平台都可以直接安装的软件，先按相同顺序写入共同的安装组。
- 某软件在一个平台只需 APT 安装，在另一个平台需要独立安装步骤时：在直接安装平台的安装列表末尾排列这些软件；在另一平台的共同安装组之后，按相同顺序排列对应独立步骤。
- 例如一个平台通过 APT 安装 Starship、fzf、Ghostty，另一个平台需要上游安装器或额外软件源，则后者按前者列表中的顺序安排独立步骤。
- 是否需要额外软件源以现有代码和目标平台的实际情况为准。Yazi 若使用官方源，应保留该来源，并将源配置和安装归到同一步；不要为了缩小差异擅自切换来源。

## 保持行为与验证

- 仅整理代码时，不改变代码含义和功能：保留安装来源、软件包集合、版本、安装路径、配置值、校验逻辑、幂等行为、错误处理和用户数据保护。
- 不要为了统一文件而给其他平台增加原本没有的功能，也不要删除平台需要的执行逻辑。确需功能变更时，应有单独明确的任务授权。
- 调整执行顺序时保持依赖关系；拆分软件源与安装分组后，在需要的位置刷新 APT 索引。
- 核对整理前后的安装包清单和有效执行语句，确认没有意外增删功能。
- 对每个修改过的 Shell 文件分别执行 `bash -n`；涉及内嵌 Python 或 XML 时检查相应语法，并执行 `git diff --check`。
- 静态整理无需运行会安装软件、修改桌面设置或覆盖用户配置的完整安装脚本。
- 提交信息使用中文，沿用仓库历史风格。
